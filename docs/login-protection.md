# Login failure protection

Release 1.2.17 adds a separate limit to `POST /api/auth/login`. A normalized
email/client-IP pair may fail ten times in a fixed 15-minute window. In-flight
attempts reserve capacity before database lookup and password work, so parallel
guesses cannot bypass the budget. Rejected attempts do not extend the window.
After expiry, sign-in is available again without operator intervention.

A successful sign-in clears only that pair's failures. Database, password-worker
or session-write failures release their reservation without consuming a failure.
Unknown users, passwordless Google accounts and incorrect password types use the
same credential-failure response and budget as existing password accounts. Login
JSON is limited to 16 KiB; valid existing password lengths and hashes are unchanged.

The limit returns HTTP 429, `Retry-After` in seconds, and `private, no-store`.
If pending work alone occupies the last slots, the retry hint is one second.
The form shows a translated wait message without clearing email/password input.
Other users on the same campus/home network, the same account at another address,
existing sessions, Google OAuth and password recovery have independent behavior.
No global account lock is created and no AI request policy is changed.

## Proxy and deployment boundary

Use the socket peer by default. Accept `X-Real-IP` only from a loopback peer;
the repository's `aws/domain-https.sh` and `aws/ip-https.sh` Nginx configurations
overwrite this header with `$remote_addr` before proxying to the local app.
Ignore `X-Forwarded-For`, invalid/duplicate headers and headers supplied by direct
remote peers. Equivalent IPv6 spellings and IPv4-mapped IPv6 are canonicalized.
Keep the backend port private. When changing the proxy topology, review this trust
boundary explicitly rather than accepting arbitrary client-supplied forwarding headers.

Counters are process-local, keyed by a random process-secret HMAC of the pair;
they do not store raw email/IP values or touch user records. Expired idle entries
are reclaimed lazily. Capacity is bounded at 10,000 pairs; full capacity rejects
new identities with a temporary HTTP 503 and a short retry hint instead of silently
evicting a live penalty or growing memory without limit. Successful idle entries
are removed immediately. Capacity pressure may temporarily delay new sign-ins.

The existing deployment uses one app process. Restarting clears counters; running
multiple workers or instances would give each its own budget. Before scaling,
move the reservation/settlement logic to an atomic shared store or enforce equivalent
edge limits. Pair scoping intentionally avoids remote global account lockout but
does not stop distributed guessing, IPv6 address rotation or password spraying.
An independent edge/WAF policy was not assumed or changed by this release.

## Verification

`tests/login-attempts.test.js` checks expiry with a controlled clock, success/error
settlement, concurrency, bounded capacity and trusted-address handling.
`tests/login-http.test.js` exercises the actual route with isolated accounts,
sessions and injected database/hash/session failures. No production password
guessing or real-user login traffic is generated by these tests.
